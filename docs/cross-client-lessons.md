# Cross-client lessons

Patterns learned from feedback across clients. Two tiers with a hard wall
between them:

1. **`## Candidate observations`** — auto-appended by the skills. An
   observation is a *signal*, not a rule: it changes NOTHING about how agents
   are built or fixed. Skills may append here freely.
2. **`## Approved house lessons`** — Brett-approved rules only. Entries land
   here (or as edits to the house docs they affect, e.g.
   `latency-playbook.md` or the MASTER TEMPLATE conventions) **only after
   Brett has explicitly approved a written proposal in chat**. Skills treat
   this section as binding house defaults.

## The approval guardrail (hard rule for every skill and agent)

**No skill or agent ever changes a house default on its own.** House defaults
means: anything in `## Approved house lessons` below, `latency-playbook.md`,
`house-persona.md`, the MASTER TEMPLATE / create-agent conventions, the
configurator agents' default values, or the skills' own instructions. The only permitted flow is:

1. Candidate observations accumulate below (automatic, no approval needed).
2. When a pattern crosses the proposal threshold — the **same feature-area
   issue recorded at 2+ distinct clients**, or a single severe issue clearly
   caused by a house default — the skill drafts the **written proposal**: the
   pattern, the evidence (client slugs + ledger FB-ids only — this file's
   privacy rules apply, no quotes/PII), the exact house-default change
   proposed, and the risk of making it.
3. **Default channel — a lesson pull request.** The skill creates a branch
   in the clone (`lesson/<short-slug>`), commits the proposed change there
   (the new lesson row and/or the house-doc edit, with the candidate row
   marked `proposed <date> — PR pending`), and opens a **pull request to
   `main` with the full proposal as the PR body**. **Brett's PR approval and
   merge IS the explicit approval** — the lesson becomes binding only when
   the PR merges. A PR closed without merging is a rejection: mark the
   candidate `proposed <date> — rejected`. This is the ONLY channel — for
   everyone, Brett included. A chat "yes" (from a teammate OR from Brett)
   never substitutes for the PR: when Brett is the operator and approves in
   chat, the skill still opens the lesson PR — his approval just means he'll
   merge it immediately. No answer means no, and approval of one proposal
   never carries over to another.

**No-git working copy (zip download):** if the working folder has no `.git`
directory — e.g. it was synced from a downloaded zip while GitHub access is
still pending — the lesson PR cannot be opened from this machine, and house
docs must NOT be edited locally (the next zip sync would silently overwrite
them). Instead, write the full proposal — pattern, evidence (client-slug +
FB-ids), exact change, risk — to `<client-folder>/pending-house-candidates.md`
and tell the user to relay it to a session that has GitHub access (e.g.
Brett's Claude Code cloud session), which opens the lesson PR for review.
The same applies to candidate rows: park them in the same file rather than
editing this one.

This gate is enforced mechanically as well as by instruction:
`.github/CODEOWNERS` makes Brett the required reviewer for every change,
and `main` should carry branch protection ("Require a pull request before
merging" + "Require review from Code Owners" — a one-time GitHub repo
setting). With that on, GitHub itself refuses any house-doc merge without
Brett's approval, regardless of who — or what — opened the PR.

Silence in this file is never a mandate: an unapproved candidate must never
influence a configurator brief, a default value, or a build decision.

## Privacy rules for this file

This file lives in the git repo, so it is stricter than the client-folder
ledgers: **no customer PII, no verbatim feedback quotes, no phone numbers,
no conversation ids — and no client names.** Clients are referred to by
their house code (`CL-A`, `CL-B`, …). The code↔client mapping never
lives in this repo: each client folder's feedback ledger carries a
`House code:` line in its header, and a skill touching a client with no
code yet stamps the next unused one into that ledger at first contact.
Brett holds the master mapping. Refer to evidence indirectly — client code + ledger
FB-id (e.g. `CL-07 FB-012`) — so the detail stays in the client folder.
